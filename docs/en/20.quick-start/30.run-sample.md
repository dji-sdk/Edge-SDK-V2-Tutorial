After completing <a href="./build-sample.html" target="_blank">Build Sample</a>, you can run the sample programs to verify the device access and data reporting workflow. The sample provides four executable programs:

| Program | Purpose |
|:---|:---|
| dock_quickstart | Minimal sample used to quickly verify the access link |
| dock_sample | Dock (dt5) single-device interactive sample, used to debug dock functions item by item |
| rid_sample | RID (dt7) single-device interactive sample, used to debug RID / ADS-B reporting |
| dock_cli | Full-feature interactive sample. Select a device identity first, then enter the corresponding function menu |

Host build output is in the `build/` directory, and aarch64 cross-compilation output is in the `build-aarch64/` directory.

## Preparation Before Running

Complete the following preparations before running the sample programs:

1. **Confirm the network connection**: Confirm that the O4 Ground Station and the device running the sample are in the same subnet. For network configuration, see <a href="./environment-prepare.html" target="_blank">Environment Preparation</a>. The sample discovers the Broker address through UDP `18830` broadcast. If discovery fails, it uses the compile-time `DOCK_BROKER_FALLBACK_IP`.
2. **Confirm that credentials are configured**: Confirm that `app_id`, `app_key`, `app_license`, and the device identifier (`device_id`) have been passed in at build time. The sample project uses the device SN as `device_id` by default.
3. **Confirm the aarch64 dependency library path**: When running on an aarch64 target board, the executable RPATH is `$ORIGIN/../lib`. Copy `third_party/aarch64-linux-gnu/lib/*.so` to the `lib/` directory at the same level as `bin/`. For temporary verification, you can also specify the dependency library directory through `LD_LIBRARY_PATH=<so-directory>`.

To temporarily switch the device identity or Broker, use environment variables to override the build-time configuration. Rebuilding is not required:

```bash
DOCK_DEVICE_SN=xxx DOCK_RID_SN=yyy DOCK_BROKER_IP=192.168.50.10 DOCK_BROKER_PORT=1883 ./build/dock_cli
```

## Quick Verification

Run `dock_quickstart` to verify whether the device can properly access the DJI Ground Station:

```bash
./build/dock_quickstart
```

The program completes the following in sequence:

1. **Connect to the Ground Station**: automatically discover the Broker address, and use the fallback address if it cannot be discovered.
2. **Report the capability set**: declare the device type. The sample accesses as a dock (dt5) by default.
3. **Perform one operation**: issue a charging command (`charge_open`) once to verify whether the functional interface is available, and then disconnect and exit.

Normally, the log contains the following key information:

```text
[discover] listening on UDP 18830 (timeout=15000ms) ...
[discover] -> broker ip=192.168.50.10
[session] connecting 192.168.50.10:1883 (sn=your-device-sn) ...
[session] connected
  <report capability_report dt5 device_type=5> topic=thing/product/<account>/state rc=0
```

If the program prints `[session] connected` and exits normally (return value 0), the access link is established.

`dock_quickstart` is the minimal access flow. Its capability set reporting uses asynchronous publishing. `rc=0` in the log indicates that the message has been sent, but does not indicate that the gateway has accepted the capability set. To confirm the capability set acknowledgement, use `dock_sample` or `dock_cli`, or call `auth_report_capability_dt5_sync()` in custom code.

## Single-Device Debugging

If you only need to debug one device type, run the corresponding single-device sample. Both `dock_sample` and `rid_sample` automatically report the capability set after connection succeeds and wait for the acknowledgement. Normally, the log contains the following information:

```text
  <capability_report ack> success result=0
```

### dock_sample (dt5)

Run `dock_sample`:

```bash
./build/dock_sample
```

The menu covers the following functions:

- Power-on and charging: `drone_open`, `drone_close`, `charge_open`, `charge_close`
- Parameters and firmware: `get_tsl`, `set_tsl`, `set_work_mode`, `get_network`, `set_network`, `get_sdr`, `set_sdr`, `set_cloud`, `org_bind`
- Periodic polling: execute `get_tsl` once every 2s, optionally with `set_tsl`
- Takeoff and landing coordination: `takeoff_prepare`, `takeoff_end`, `landing_prepare`, `landing_end`, and `abnormal_recovery` progress reporting
- Service self-test: replay five inbound service requests to verify whether handlers are registered correctly

For menu items marked with `*`, the program prompts for parameters one by one. Press Enter to use the default value or skip the parameter.

### rid_sample (dt7)

Run `rid_sample`:

```bash
./build/rid_sample
```

The menu covers one-time `rid_infos` reporting, one-time `adsb_infos` reporting, and starting or stopping periodic RID / ADS-B reporting. Periodic reporting refreshes batches every 2s and follows the 5Hz rate limit.

## Full-Feature Debugging

`dock_cli` is a two-level menu and connects only one device identity at a time. After startup, select the dock (dt5) or RID device (dt7). The program connects with the selected identity, reports the corresponding capability set and verifies the acknowledgement, and then enters the corresponding function menu. When the submenu exits, the current identity disconnects.

```bash
./build/dock_cli
```

The device identity selection menu is as follows:

```text
===== Select connecting device identity (this CLI connects one at a time) =====
   1  third-party dock device (dt5)
   2  RID device              (dt7)
```

The dt5 submenu is equivalent to `dock_sample`, and the dt7 submenu is equivalent to `rid_sample`. The two device identities build their own session parameters and use their own `device_id` values and accounts.

## Message Log

During integration testing and troubleshooting, enable the message log to view the actual JSON messages sent and received. Use either of the following methods:

**Method 1: Toggle at runtime**

`dock_sample`, `rid_sample`, and `dock_cli` all support pressing `w` at runtime to toggle the message log.

**Method 2: Use an environment variable at startup**

```bash
THING_MODEL_LOG_LEVEL=debug ./build/dock_cli 2>&1 | grep -E 'PUB|RCV'
```

If a request (`PUB`) and its reply (`RCV`) have the same `tid`, the request and reply are successfully paired. If the `tid` does not match or no reply is received, the message is usually not delivered or has timed out.

For the complete Topic, payload, and field descriptions of each function, see the <a href="../api-reference/rid.html" target="_blank">RID Device</a> and third-party dock device API chapters (<a href="../api-reference/dock/charging.html" target="_blank">Power-On and Charging</a>, <a href="../api-reference/dock/flight.html" target="_blank">Takeoff and Landing Coordination</a>, <a href="../api-reference/dock/dock-config.html" target="_blank">Dock Configuration</a>, and <a href="../api-reference/dock/thing-model.html" target="_blank">Thing Model Interface</a>).

## RID / ADS-B Reporting Notes

Pay attention to the following items when debugging RID / ADS-B reporting:

1. The wire unit of ADS-B `speed` is km/h. FlightHub 2 divides the value by 3.6 and displays it in m/s. After ADS-B speed is entered, `dock_cli` prints the conversion result. For example, entering `941` prompts `FlightHub 2 will display 261.4 m/s`.
2. Periodic reporting overwrites values reported manually in one-time reports. The periodic thread refreshes data every 2s. Because the sample is not connected to a real radar data source, it resends the target from the last one-time report when the cache is empty in the current period. Therefore, after a new one-time report is sent while periodic reporting is enabled, it may be overwritten by the repeated reporting of the previous target 2s later. When debugging parameters, use menu item `33` to stop periodic reporting first, or observe periodic reporting separately as a stable data source.
