This section introduces the development environment required to access ESDK V2, including hardware devices, network connections, software dependencies, and obtaining the Broker address.

## Development Devices

- A DJI O4 Ground Station, which serves as the carrier platform for device access and data forwarding.
- An access device or its development carrier (such as a Raspberry Pi or other Linux device), used to run the access program.
- A switch or router, used to connect the O4 Ground Station and the access device to the same LAN.

## Hardware Connection

The O4 Ground Station provides two network ports: a LAN port and a WAN port. Ethernet access devices such as RID and third-party docks connect in the following ways respectively. For detailed descriptions of the network ports, see <a href="../basic-intro/hardware/hardware-port.html" target="_blank">Hardware Port</a>.

### RID Device Connection

Ethernet access devices such as RID connect to the O4 Ground Station through a network port, supporting the following two connection methods.

:::tip Recommendation:
For initial access and debugging, Method 1 (direct LAN connection) is recommended. The Broker address is fixed and the configuration is the simplest.
:::

#### Method 1: Direct LAN Connection

The access device connects directly to the LAN port (the right network port) of the O4 Ground Station via a network cable. The access device IP must be in the `192.168.50.xx` subnet, and the Broker address is fixed at `192.168.50.10:1883`, requiring no additional query.

<img src="https://terra-1-g.djicdn.com/71a7d383e71a4fb8887a310eb746b47f/esdk-v2/network-topology/Method%201_Direct%20LAN%20connection_1_en.svg" alt="Fig. ESDK device connected to O4 Ground Station via LAN port" />

#### Method 2: WAN Port via a Router

The access device and the WAN port (the left network port) of the O4 Ground Station are connected to the same router respectively. The IP of the O4 Ground Station is dynamically assigned by the router, and can be obtained automatically through [Obtaining the Broker Address](#obtaining-the-broker-address), or confirmed through the enterprise application.

### Third-Party Dock Connection

The third-party dock system consists of components such as the drone, the wireless charging module, the third-party dock, and the O4 Ground Station. The overall connection is shown in the figure below, and the connected components and their purposes are listed in the table below the figure.

The power-on and charging capability interfaces of ESDK V2 must be used together with the DJI wireless charging module. The wireless charging module is provided by DJI. To obtain it, email [dev@dji.com](mailto:dev@dji.com) to contact the SDK technical support team.

| Connection | Description |
|:---|:---|
| SDR | The image transmission link between the drone and the O4 Ground Station |
| Wireless Charging / Bluetooth Connection | The charging and Bluetooth connection between the wireless charging module and the drone |
| CAN-LAN | The communication between the wireless charging module and the O4 Ground Station |
| AC-DC Power Supply | The third-party dock supplies power to the wireless charging module |

| Cloud Interface | Data reporting between the O4 Ground Station and FlightHub 2 PaaS / a third-party cloud |

Here, CAN-LAN connects to the CAN-LAN adapter through PIN13 (CAN_H) and PIN16 (CAN_L) of the 42.CORE/F/N connector of the ACDC component, enabling communication between the dock and the O4 Ground Station. ## Log In to the Access Device

After the hardware connection is complete, log in to the access device (such as a Raspberry Pi). Subsequent software installation and compilation operations are all performed on the access device. Taking SSH as an example:

```bash
ssh <username>@<access device IP>
```

:::tip Note:
The operating computer and the access device must be in the same subnet to connect via SSH. They can be connected directly via a network cable or through a router. Before logging in, confirm the IP address of the access device and set the operating computer to the same subnet.
:::

## Software Installation

The access device side needs to install the MQTT client dependency. Taking development based on mosquitto as an example, run the following on an Ubuntu/Raspberry Pi system:

```bash
sudo apt install -y libmosquitto-dev
```

## Obtaining the Broker Address

After the access device is powered on, the Broker address of the O4 Ground Station can be obtained automatically by listening to the UDP broadcast, without hard-coding the IP.

### Overall Flow

1. The access device powers on, and the network port obtains an IP via DHCP.
2. The device listens on UDP port `18830`.
3. The O4 Ground Station broadcasts a packet through the network port approximately once every 1 second.
4. After receiving the broadcast, the device parses out the `ip` field and uses that IP to connect to MQTT (port `1883`).
5. If no broadcast is received, it can fall back to the default address `192.168.50.10:1883` and connect directly.

### Broadcast Packet Format

The packet is a single line of ASCII text, a single UDP packet. Fields are separated by `|`, and keys and values are separated by `=`. It contains no line breaks or spaces, and the format is not JSON:

```
MQTTBRK|v=1|id=BMGDNAB0010122|name=O4_Ground_Station|ip=192.168.50.10|seq=32
```

| Field | Description |
|:---|:---|
| MQTTBRK | Fixed magic header, by which the device identifies the packet. Packets that do not conform to this format should be ignored. |
| v | Protocol version, currently 1. Packets with an unrecognized version should be ignored. |
| id | The SN (unique ID) of the O4 Ground Station, used to filter the target when multiple devices coexist. |
| name | A human-readable name, used only for display, and may be empty. |
| ip | The IP of the network port where this broadcast is located; the device uses this IP directly to connect to MQTT. |
| seq | The broadcast sequence number, incrementing from 0; a return of seq to 0 indicates that the O4 Ground Station has restarted, and the device should reconnect. |

:::warning Note:
The packet does not contain a port number; the Broker port is fixed at 1883.
:::

### Listening Parameters

| Item | Configuration |
|:---|:---|
| Protocol | UDP |
| Port | 18830 |
| Bind Address | `0.0.0.0` (must bind to the wildcard address; binding a specific NIC may cause some broadcasts to be missed) |
| socket option | `SO_REUSEADDR=1` (must be set before bind) |
| Receive Buffer | ≥ 4096 bytes |

### Command-Line Verification

After the device is powered on and connected to the same subnet, you can use tcpdump to confirm whether the broadcast reaches the local machine:

```bash
sudo tcpdump -i any udp port 18830 -A
```

Under normal circumstances, the terminal will continuously output packet content containing `MQTTBRK|v=1|id=...|name=...|ip=...|seq=...`.
